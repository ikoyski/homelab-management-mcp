# Homelab Management MCP — setup guide

Complete these steps in order. Existing deployments can use each guide as an audit checklist.

## Components and connection paths

| Component | Responsibility | Connection |
|---|---|---|
| Proxmox VE | Nodes, QEMU VMs, LXC guests, storage | MCP → Proxmox HTTPS API |
| Docker Engine | Runs workloads | Portainer Agent → Docker Engine |
| Portainer Server | Central Docker API | MCP → Portainer HTTPS |
| Portainer Agent | Remote Docker access | Portainer Server ↔ Agent |
| Webtools Identity Server | OAuth/OIDC authentication | AI client → Auth |
| Private Spring Config Server | Credentials and runtime properties | MCP → Config Server |
| Private CA / Java truststore | TLS trust for private upstreams | MCP JVM validates Proxmox/Portainer |
| Tunnel / ingress | Protected MCP access | Tunnel → MCP:8083 |

The MCP does not need SSH access to guests, does not mount the Docker socket, and does not connect directly to Agents or remote Docker Engines.

## Recommended order

- [ ] Create the Proxmox read-only API user and token.
- [ ] Prepare Docker Engine on selected hosts.
- [ ] Deploy Portainer Server and connect remote environments with Agents.
- [ ] Create a Portainer API key and store it privately.
- [ ] Issue TLS certificates from a private CA with correct SANs.
- [ ] Build a Java truststore containing public roots plus private CA certificates.
- [ ] Add application configuration to the private Config Server.
- [ ] Prepare private Docker networking, Compose, and tunnel routing.
- [ ] Deploy MCP and verify internal health.
- [ ] Configure OAuth/MCP access for an AI client and validate the tools.

## Values to prepare privately

| Value | Example format | Used by |
|---|---|---|
| Proxmox URL | \`https://<proxmox-dns-name>:8006\` | \`homelab.proxmox.api-url\` |
| Proxmox token ID | \`<user>@<realm>!<token-name>\` | \`homelab.proxmox.token-id\` |
| Proxmox token secret | Generated once | \`homelab.proxmox.token-secret\` |
| Portainer URL | \`https://<portainer-dns-name>:9443\` | \`homelab.docker.portainer.base-url\` |
| Portainer API key | Generated by Portainer | \`homelab.docker.portainer.api-key\` |
| Docker host keys | \`<host-key>\` | Private environment allowlist |
| Central Webtools UUIDs | UUID values | \`homelab.security.allowed-users\` |
| Config Server URL | \`http(s)://<private-host>:<port>\` | \`CONFIG_SERVER_URL\` |
| Config Server credentials | Secret values | \`CONFIG_USER\`, \`CONFIG_PASSWORD\` |
| Truststore path/password | Private path and secret | JVM truststore settings |

The Proxmox token secret is shown only at creation. Keep credentials in a password manager/private secret store, not shell history or AI prompts.

## Network requirements

Permit only required paths:

- MCP → private Config Server.
- MCP → Proxmox HTTPS API (normally TCP 8006).
- MCP → Portainer HTTPS API (normally TCP 9443).
- Portainer Server → local Docker Engine through its documented local connection.
- Portainer Server → remote Agent listener (commonly TCP 9001) over the private network.
- AI client → authenticated MCP ingress.
- Internal monitoring → Actuator port 8082, if required.

Do not expose Proxmox, Portainer, Docker Engine, Agent listener, Config Server, or Actuator publicly. The ingress should route to MCP only. Adapt ports to your environment; do not copy another site's private addresses.

## Acceptance checklist

- [ ] Proxmox token authenticates and has intended read privileges only.
- [ ] Portainer Server reports intended local and Agent-managed environments Up.
- [ ] Portainer API key is stored only in private configuration.
- [ ] TLS verification succeeds for Proxmox and Portainer.
- [ ] Java truststore preserves public roots and includes private CA certificates.
- [ ] Config Server returns the correct application configuration.
- [ ] Only approved Docker host keys and central identities are allowlisted.
- [ ] Internal health succeeds on port 8082.
- [ ] Authenticated MCP endpoint works on port 8083; unauthenticated requests are rejected.
- [ ] Proxmox and Docker tools return expected data through an authenticated AI client.
- [ ] Targeted log retrieval works; do not assume redaction removes every secret.
- [ ] No write-capable tools, Docker socket mounts, or public management-port routes exist.

## Existing deployments

Do not recreate service accounts, tokens, certificates, or Portainer environments blindly. Audit what exists, verify permissions and TLS trust, then map existing values into private configuration. Token rotation and certificate replacement are maintenance tasks that can interrupt a running deployment.
